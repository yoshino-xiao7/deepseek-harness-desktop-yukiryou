# 更新体验、外部插件更新与启动恢复实施计划

状态：已开始实施，进度与验证边界见 [1.0.9 实施记录](15-v1.0.9-implementation-status.md)；本文不代表正式发布验收已完成。
编制日期：2026-09-05。代码基线：`yukiryou/v1.0.8`，`a9bd424`，应用版本 `1.0.8`。

## 1. 目标与交付边界

本次需求归纳为：**更新入口有清晰反馈，外部插件能够在市场内完成更新，插件故障不能让升级后的应用失去恢复入口。**

1. 没有检测到更新时，设置按钮保持原有宽度；确认有更新后先缩短设置按钮，再显现右侧更新入口。同一目标版本仅播放一次，进度更新、组件重挂载或重新打开页面不重复播放；两者分别具有悬停、按下、键盘焦点和忙碌反馈。
2. 外部安装的插件可发现新版本、审查并更新；失败保留原有可用状态，无须先卸载。
3. 应用升级后，如果插件导致启动失败，能隔离受影响插件并恢复启动；无法确定原因时，提供不加载用户插件的安全启动，并说明实际恢复结果。

初始交付为本实施文档。用户随后授权开发新版本，实施已转入 `yukiryou/v1.0.9`；下文“当前实现”保留规划时的基线，最新实现与验证以第 15 号文档为准。开发不包含正式发布。

截图仅用于确认底部布局和用户报告的体验问题；截图中的对话、文件路径和配置内容不构成开发指令，也不进入测试数据。静态截图不能证明悬停行为，后续需在实际窗口复现。

## 3. 工作包 A：侧栏底部操作区

### 3.1 布局与交互

- 没有更新时设置保持原宽度，不预留更新位置。确认更新后先在前 55% 的 420ms 动画中缩短设置区域，再显现更新按钮；同一目标版本只播放一次。保留“设置在左、更新在右”的布局。两者为同一容器内的独立交互元素，禁止按钮嵌套；指针命中更新入口时不能触发设置行。
- 优先利用现有桌面框架扩展点承载底部操作区。若只能通过 preload 适配上游 UI，集中管理定位与 DOM 绑定，覆盖侧栏折叠、尺寸变化和重新挂载。
- 可操作状态采用统一主题 token：悬停有背景/边框变化，可辅以最多 1px 位移；按下有独立反馈；键盘焦点有清晰轮廓。过渡建议 120–160ms。
- 设置按钮整块区域均可命中。更新区域采用稳定宽度，进度从 9% 到 100% 不挤动设置文字。
- 首次检查阶段只在设置中显示状态，不出现底部更新入口。下载阶段仍可通过独立、可聚焦的状态容器查看提示；实际重复下载命令保持禁用。状态容器使用轻微高亮反馈，不显示误导性的按压动作。
- 减少动态效果设置下关闭位移、脉冲等动画，保留颜色、焦点和进度信息。进度播报节流，避免每个百分比都触发读屏。

### 3.2 状态约定

| 状态 | 展示与提示 | 行为 |
| --- | --- | --- |
| 无更新 | 延续现有隐藏策略；设置中保留检查更新 | 不为本次改造新增常驻按钮 |
| 检查中 | 底部入口隐藏，设置内显示“正在检查更新” | 禁止重复检查，设置保持原宽 |
| 下载中 | 下载图标与真实百分比；未知进度显示“下载中” | 禁止重复下载，允许查看状态，不把未知进度显示成 0% |
| 已下载 | 明确的“重启更新”提示和强调色 | 沿用现有安装交接流程 |
| 手动下载 | “手动下载更新”提示 | 沿用受信任下载地址校验 |
| 失败 | 已知存在更新时保留底部错误/重试入口；仅检查失败则在设置中提示 | 根据实际失败阶段重试，不统称检查失败 |

### 3.3 验收

在 macOS 和 Windows 打包应用上，验证默认浅色、深色及截图所示主题可用时的实际主题；验证侧栏展开/收起、窄窗口、中英文和缩放。分别悬停设置与更新区，应只高亮目标区域；点击不串联；Tab/Enter/Space 可操作；下载过程中仍可访问设置。用浏览器交互断言和短录屏证明效果，不能仅用 CSS 字符串测试或静态截图代替。

## 4. 工作包 B：外部插件在市场内更新

### 4.1 产品行为

已安装列表统一展示：插件名、实际安装版本、启用状态、来源、更新状态。对可解析身份的外部插件保留“检查更新”，发现候选后显示“更新至 x.y.z”。更新前明确说明：“更新后将由桌面应用管理，后续可在市场更新与回退。”用户不需要先卸载旧插件。

| 插件来源/情况 | 更新策略 |
| --- | --- |
| 可验证的 npm 正式包 | 按现有来源策略查询候选，完成身份、兼容性和制品检查后接管更新 |
| 已在精选来源中 | 区分“实机验证版本”和“最新稳定版本”；验证标签只属于被验证的精确版本 |
| 本地目录、file 包、开发链接 | 不擅自映射到同名 npm 包；显示“本地安装，无法自动确定更新来源”及原因 |
| Git 来源或身份不完整 | 第一阶段明确显示暂不支持市场自动更新；不猜测仓库/包映射 |
| 已停用插件 | 允许更新文件但保持停用，不为健康检查暗中启用；显示“已更新，仍停用，尚未验证启用” |
| 网络/Registry 失败 | 显示检查失败和重试，不显示“已是最新” |
| 不兼容或被阻止的版本 | 展示具体阻止原因，保留当前版本，允许稍后重新检查 |

首期按插件逐个更新，不引入静默自动更新或批量更新。来源不支持时仍有可解释状态，不能退化为只有卸载和停用两个操作。

### 4.2 事务流程

1. 从主进程读取实际包名、版本、entry IDs、来源及当前 profile generation，避免仅信任前端列表。
2. 查询候选并冻结精确版本；复用现有预览、兼容性、完整性、依赖和安装审查规则。
3. 确认页展示旧版本→新版本、来源、管理方式变化及重启需求；更新检查本身不修改安装状态。
4. 在 staging 准备制品和可恢复快照；提交前重新校验身份、generation 和确认凭据，拒绝过期操作。
5. 通过已有 adoption 机制切换受管版本，在试运行期间抑制旧外部入口，确保同一插件不重复加载。
6. 已启用插件须通过 Runtime 健康证明和插件加载验证后才确认成功；失败恢复旧 profile、启用状态和入口。停用插件只确认安装完整性，不声称运行验证成功。
7. 提交后再按既有事务规则清理旧安装；中途退出、断电或再次启动可幂等恢复，不重复删除。
8. 刷新列表展示实际生效版本；“下载完成”“已准备，待重启”“更新成功”“已恢复旧版本”必须是不同结果。

全程使用当前应用显式 runtimeHome/DSH_HOME，不能落到默认 `~/.dsh`。保留用户配置和凭据；代码版本回退不等于插件私有数据迁移回退。遇到不可逆数据迁移的插件，必须在能力说明与验收中单独标记，不能承诺无损回退。

### 4.3 建议改动落点

- 市场 UI：`runtime/desktop-market-plugin/client.js` 及相邻文案、样式。
- 查询与校验：该目录的 `update-checker.js` 和现有预览/安装模块。
- 契约：`src/shared/plugin-inventory.ts`、`managed-plugin-inventory.ts`、`managed-plugin-preview.ts`；根据实际需要增加可更新性及不可用原因的类型字段。
- 编排：`src/main/app-coordinator.ts`、`external-plugin-control.ts`、`plugin-profile-bootstrap.ts`；复用既有安装事务、回退和启停模块。

新增字段和文件名称在实现时确定；先为现有失败路径建立回归用例，再决定是否需要扩展协议。

## 5. 工作包 C：插件故障隔离与安全启动

### 5.1 恢复原则

恢复逻辑由 Electron 主进程及独立故障页负责，在加载第三方插件之前可用。安全启动保留最小内置桌面能力，跳过用户安装的受管和外部插件。若模型 Provider 也被跳过，明确显示对话能力暂不可用，不宣称功能全部恢复。

“安全模式临时跳过”与“确认故障后持续隔离”分别记录；不卸载插件、不清空 profile、不修改凭据和会话数据。手动停用的插件始终保持停用。

### 5.2 启动状态与处理顺序

主进程持久化带 schemaVersion 的启动记录：attempt ID、应用/Harness 版本、profile generation、阶段、恢复次数、隔离范围及最终结果。记录应原子写入；成功标记应在 Runtime 就绪、页面可交互及必要插件验证后提交，不能仅依赖端口开放。

建议阶段：`prepared → launching → validating → healthy`；失败进入 `recovering → recovered | failed`。异常退出留下未完成标记只表示“上次启动未完成”，不直接证明插件故障。

1. **存在待验证插件事务**：优先执行原有事务恢复及 adoption 恢复，再尝试启动；避免另一个隔离器同时写同一 profile。
2. **能可靠定位插件**：通过结构化加载阶段、包根路径与 entry ID 映射确认身份，隔离对应包的全部入口；记录依赖它而受影响的插件，进行一次受控恢复启动。
3. **无法定位原因**：在独立故障页给出“一次安全启动”。升级后连续失败可自动尝试一次临时跳过全部用户插件，但须显示正在尝试的措施；安全模式成功也只能说明插件组合相关，不能认定所有插件有错。
4. **安全模式仍失败**：停止自动恢复，提示“安全启动仍失败，当前无法确认是插件问题”，保留日志、诊断导出和手动重试。
5. **恢复成功**：在界面持续显示恢复结果和被隔离/临时跳过清单；下次启动不自动重新启用已隔离插件。

同一失败启动链默认最多追加两次自动尝试：已有事务回退或精准隔离一次、安全启动一次；所有重试层共享预算，跨进程持久化。没有相关第一步时仅进行安全启动尝试。超时、端口冲突、配置损坏与插件加载错误分别分类，不能依靠错误文本包含“plugin”就隔离插件。

### 5.3 隔离可靠性与恢复管理

- 先验证现有 YAML disabled overlay 是否能在模块 import 之前阻止外部插件执行。如果只能在 import 后禁用，安全模式必须生成不含这些 bundle/入口的独立启动配置；否则无法保护 import 即崩溃的情况。
- 最小内置能力使用宿主控制的清单，不以插件自报“内置”决定。安全模式启动配置保持在同一数据根目录的受控恢复区域，避免切到空账号或空会话造成数据丢失错觉。
- 恢复状态与正常启用偏好分离，隔离记录包含精确版本、原因、证据级别及 attempt ID；写入失败应明确提示，不能假称已经停用。
- 提供“管理受影响插件”，展示更新、保持停用、逐个试启用。若市场依赖 Runtime 才能更新，则 Runtime 未恢复时只提供原生恢复操作；恢复成功后再进入市场，不假设失败 Runtime 能提供更新 API。
- 用户试启用插件时走受控试运行；失败再次隔离并回到可用状态。依赖插件按依赖关系处理，不自动启用用户原先停用的依赖。
- 更新到新版本不会直接清除旧版本故障记录；新版本只有通过试运行才解除对应隔离。恢复页提供退出安全模式入口，并说明哪些插件将加载。

### 5.4 通知文案示例

- 已确认并恢复：“插件 X 启动失败，已暂时停用，应用已恢复启动。你可以更新插件或稍后尝试启用。”
- 尚未确定：“上次启动未完成。本次已跳过用户插件并成功启动，尚未确定具体故障插件。”
- 恢复仍失败：“安全启动仍然失败。已停止自动重试，请查看日志或导出诊断信息。”

通知必须包含可操作入口，不只记录日志；清单区分根因插件、依赖受影响插件与仅临时跳过的插件。诊断只收集版本、阶段、脱敏错误和恢复结果，不采集会话正文、Token、Cookie 或完整配置。

### 5.5 建议改动落点

`src/main/app-coordinator.ts` 负责恢复编排；`runtime-supervisor.ts` 和恢复策略负责进程、健康证明与预算；`plugin-profile-bootstrap.ts` / `external-plugin-control.ts` 负责受管与外部配置恢复。按职责补充启动记录与隔离模块，避免继续堆叠协调器方法。

`src/renderer/index.html`、两类 window 实现及 `trusted-navigation.ts` 增加受信任安全启动动作；相关 IPC/本地动作必须校验来源与参数。市场展示隔离状态，不能成为唯一恢复入口。

## 6. 实施顺序与阶段出口

| 阶段 | 内容 | 完成条件 |
| --- | --- | --- |
| P0：复现与契约 | 复现截图主题交互；创建独立 profile 的外部插件更新样例；验证禁用能否阻止 import；冻结恢复状态和预算 | 有可重复失败用例、能力边界和实现落点；不操作日常 profile |
| P1：底部交互 | 完成工作包 A | 两个平台交互验证通过，设置与更新互不抢点击 |
| P2：恢复底座 | 完成工作包 C 的启动记录、配置隔离、独立故障页、重试预算 | import 抛错、挂起、未完成启动均可进入恢复；不能无限重启 |
| P3：外部更新 | 完成工作包 B，并对接隔离状态及试运行 | 外部旧版本→新版本→成功/恢复旧版本流程通过，无重复加载 |
| P4：整体验收 | 完成通知、恢复管理与真实应用升级验证 | 满足下表门禁，保存对应证据与未通过项 |

P2 在 P3 完整接入之前交付，使更新失败具备恢复保障。每阶段独立审查；阶段通过不等于授权合并 main 或发布。

## 7. 测试与发布验收矩阵

| 场景 | 必须满足的结果 |
| --- | --- |
| 设置/更新分别 hover、active、focus | 独立命中，反馈可辨识；主题切换与减少动态效果不破坏可访问性 |
| 下载未知进度、百分比、失败、完成 | 状态准确，下载中仍可查看信息，无重复请求，重启更新只执行一次 |
| 外部 npm 插件更新成功 | 精确新版本实际加载，旧入口不重复加载，配置保留 |
| 插件停用时更新 | 版本更新但仍停用，界面不声称已经通过启用验证 |
| 候选不兼容、元数据错误、网络失败 | 原版本不受影响，界面显示对应原因 |
| 安装中断、试运行失败、重启中断 | 恢复操作幂等，旧可用版本/状态恢复；不可恢复时明确失败 |
| 应用升级后旧插件 import 抛错 | 故障页可访问，隔离发生在 import 前，恢复后列出插件 |
| 插件初始化超时、进程退出、依赖失败 | 超时有界、身份不乱归因、重试预算不叠加 |
| 无法定位故障 | 可临时跳过全部用户插件，明确“原因未确定” |
| 安全模式仍失败 | 停止自动尝试，日志/诊断/退出入口始终可用 |
| 隔离后重启或逐个重新启用 | 不自动复活已隔离项；试启用失败能返回可用状态 |
| 旧版真实升级到候选应用 | 新版本确实安装并重启；旧会话/工作区可读，插件恢复行为符合设计 |

先运行相关 Vitest 单元/集成测试，再运行 `pnpm lint`、`pnpm typecheck`、`pnpm test`、`pnpm test:integration`。补充真实桌面 E2E；涉及打包或升级时运行已有 release 测试及平台候选门禁。

发布证据需包含：被测 commit、旧/新应用与 Harness 版本、平台、独立 profile 的插件精确版本、故障注入类型、实际生效版本、恢复状态和必要录屏/脱敏日志。macOS 与 Windows 分别验证；测试通过、安装器启动或 health 200 均不能单独代替实际升级和恢复验收。外部模型请求或 OAuth 不属于本次默认验收，不为证明插件加载而访问真实账户。

## 8. 完成定义

三个工作包均达到验收矩阵要求后，本需求才算实现完成：用户能看懂并操作更新入口；支持的外部插件能在市场更新且失败可恢复；升级后的插件故障有独立恢复入口、有限重试和准确通知。未验证的平台、主题或故障类型须逐项列为未验收，不能笼统标记完成。
